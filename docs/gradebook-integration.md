## Unified grade entry

Grade Management now has one section-scoped interface. Select semester, course, section and assessment; edit one score column, save pending drafts, and publish the selected assessment or eligible final grades in place. Assessment switching preserves pending edits across the course. Search does not narrow publication recipients; confirmations list every recipient. Course management owns assessment structures and grading rules. Legacy gradebook/grades routes redirect to Grade Management; the assessments route redirects to course configuration. Existing request contracts and publication privacy rules below remain applicable.

# Gradebook frontend contract

No backend or database was implemented. Existing endpoints remain unchanged. New calls below use the existing API adapter and reject when it is unconfigured.

Portal data additions (all empty/null by default):
- `semesters`: `{ id, name }`.
- `assessmentStructures`: `{ courseId, version, inUse, locked, assessments: [{ id, name, weight, maximum }] }`. There must be exactly one structure per course, shared across sections. The frontend locks edits when any course grade record exists (including other sections), while scores are unsaved, or when `inUse`/`locked` is set. The service must provide usage metadata even when grade records are omitted/paginated, reject concurrent use/edit races and enforce the unique course constraint. Structural migrations require a separate reviewed/versioned process, not this editor.
- `gradingRules`: `{ version, decimals, roundBeforeGrading, bands: [{ minimum, letter, points }] }`. No default grade boundaries are invented. Points use 0–4; thresholds cover [0,100] using inclusive minima, with zero required.
- Sections need `semesterId` and `courseId`; enrollments need `semesterId`, `sectionId`, `studentId`, `status`. Dropped/Cancelled/Withdrawn enrollments are excluded. The roster is intersected with actual student records and deduplicated.
- Grades need `semesterId`, `sectionId`, `courseId`, `studentId`, `version`, `published`, `status`, plus the existing display fields. Assessments carry `assessmentId`, `name`, `weight`, `maximum`, `score`, and independent `published` / `status` fields. Final publication does not implicitly publish assessments. Assessment publication does not publish the final grade.

Proposed frontend requests:
- `PUT /assessment-structures/:courseId`: version and assessment array. The service must reject incompatible edits when recorded grades reference a structure, or explicitly migrate and version them.
- `PUT /settings/grading`: grading scale, rounding policy and version. Validate thresholds/points and version conflicts.
- `PUT /gradebooks/:sectionId`: semesterId, courseId, structureVersion, gradingRulesVersion, `published: false`, `assessmentPublication: "preserve-unchanged"`, rows (`studentId`, version, assessmentId/score entries). Only changed students are included. Blank scores are null. The service must invalidate changed students' final publications and only edited assessment publications, preserve unchanged assessment publications and leave all other students untouched. Revisions affecting published records require confirmation.
- `PATCH /gradebooks/:sectionId/publication`: semesterId, courseId, structureVersion, gradingRulesVersion, `type: "assessment" | "final"`, optional assessmentId, `published: true`, rows (`studentId`, version). This metadata-only operation never edits scores. Assessment release requires valid saved marks for that assessment, independently of other missing marks. Final release requires all valid scores and configured rules. Admin can target one final result or all eligible results; filters do not change eligibility scope. Reject duplicate/mismatched records, non-enrolled targets, stale versions, unsaved edits and incomplete/invalid results. Confirmation lists exact affected students.

The service must authorize Admin only, validate enrollment ownership and versions, recompute all totals and grade points, and atomically save/publish the requested targets or return an error. The frontend's development role switch is not authentication or authorization. Gradebook deliberately sends raw scores, not trusted calculated grades. Publication actions and calculated final results appear beside the single assessment score-entry table in `/admin/grade-management`. Course configuration is in `/admin/courses?view=assessments`. Legacy grade routes redirect to the unified screen.

Local edits are transient and marked unsaved. No localStorage or optimistic database writes. A successful response is required for save/publication feedback; changing class discards local edits. Students see only their explicitly published final records and independently published assessment marks (`published: true`, status neither Draft nor Unpublished). Missing publication metadata stays private. Assessment-only projections omit final total, letter, GPA and private fields; final projections remove unpublished assessments. Without a current-student identity or during financial holds, both projections are empty, including when a registration-only override exists. The service must omit unpublished values from its responses, enforce the same restrictions and return GPA summaries based solely on authorized published final records.

Weighted result = sum(score / maximum × weight). Missing scores are incomplete, never inferred zero. Grade thresholds compare the unrounded result by default; an administrator can enable rounding before grade assignment. The per-course GPA/grade-point value is not a cumulative GPA calculation; cumulative GPA remains a server-provided summary.
